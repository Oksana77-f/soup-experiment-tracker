# Правила разработки Soup Experiment Tracker

Начинай с [PRD.md](PRD.md) и текущего состояния репозитория. Рабочие допущения, нагрузочный вердикт и границы доказательств сверяй с [отчётом](docs/results.md). Правила стиля применяй к новому и изменяемому коду. За изменением контракта должны следовать изменение PRD и проверка его потребителей.

## Стек и границы модулей

| Слой | Стек | Основные файлы |
|---|---|---|
| UI | React 19, TypeScript в строгом режиме, Vite 7 и Node.js 22 для сборки, CSS, браузерные Fetch и EventSource | `frontend/src/main.tsx`, `api.ts`, `useRun.ts`, `style.css` |
| API и сессии | Python 3.11 в Docker, FastAPI, Pydantic, Uvicorn, itsdangerous, sse-starlette | `tracker/app.py`, `auth.py`, `models.py`, `settings.py` |
| Данные | PostgreSQL 17, psycopg 3 и пул соединений, параметризованный SQL | `tracker/schema.sql`, `db.py`, `admin.py` |
| CLI и проверки | HTTPX, pytest, pytest-asyncio, Playwright Chromium, Docker Compose | `tracker/cli.py`, `tracker/send.py`, `tests/`, `scripts/load.py` |

Конкретные версии бери из `frontend/package.json`, `frontend/package-lock.json`, `requirements.txt` и `requirements-test.txt`. При изменении зависимости обновляй соответствующий lock-файл или точную версию в списке зависимостей. Предпочитай существующую библиотеку или стандартный API, если они покрывают задачу.

## Имена, типы и читаемость

- Компоненты и публичные типы TypeScript — `PascalCase`, например `RunView` и `Snapshot`. При выделении компонента в файл используй имя компонента с расширением `.tsx`. Хуки называй `use…`, например `useRun`. Переменные, функции и обработчики — `camelCase`. Булевы имена должны читаться как условия, например `isLoading` или `hasSession`.
- Для новых props, API-ответов, SSE-событий и экспортируемых интерфейсов объявляй типы TypeScript. Для очевидных локальных значений используй вывод типов. На границе с сетью проверяй форму и значения данных во время выполнения. В JSON сохраняй имена контракта `batch_id`, `last_seq`, `seq` и `step`. CSS-классы — `kebab-case`.
- Python-файлы, функции, параметры и поля — `snake_case`, классы — `PascalCase`, константы — `UPPER_SNAKE_CASE`. Новые публичные функции и границы модулей аннотируй. Параметры и JSON схемы проверяй моделями Pydantic и существующими проверками. Таблицы, столбцы и индексы называй в `snake_case`.
- Имена тестов описывают сценарий и ожидаемый результат. Используй понятные доменные имена `run_id`, `batch_id`, `lastApplied` и `pendingBatch`. Комментарии объясняют инвариант, причину блокировки или пограничный случай.

## Запреты и инварианты

- Не добавляй устаревшие или неподдерживаемые библиотеки, параллельные реализации той же функции или новую инфраструктуру без отдельного обоснования. Сохраняй текущий способ запуска и существующие зависимости в рамках задачи.
- Не используй явный `any`, `@ts-ignore` и приведения типов для обхода сетевой валидации. Не отключай `strict`. Не добавляй параметры и вспомогательные функции без потребителя.
- Не собирай SQL строковой интерполяцией. Не бери `project_id` из входных данных как доказательство прав. Не передавай ключи в URL, не сохраняй секреты в JS-хранилищах и не логируй заголовки авторизации, cookie или тела метрик.
- Не разрешай запись по cookie. Сохраняй одинаковый `404` для чужого и отсутствующего запуска, `no-store` на защищённых ответах и проверку отзыва ключа при чтении SSE. Для изменений cookie-сессии соблюдай контракт проверки `Origin`.
- Не используй глобальную PostgreSQL sequence для `seq`. Блокируй строку запуска до проверки дублей. Новые метрики, `last_seq` и подтверждение сохраняй в одной транзакции. Сохраняй составные уникальные ограничения и неизменный пакет при повторе.
- Не вводи неограниченную очередь на подписчика. Возвращай соединение в пул до отправки SSE. Сохраняй чтение истории и новых событий по одному курсору. Закрывай SSE, таймер и незавершённые запросы при уходе со страницы.
- Не добавляй тестовые флаги или эндпоинты в рабочее приложение. Не синхронизируй конкурентные тесты фиксированными паузами. Используй события, барьеры и ожидания условий с тайм-аутом. Сохраняй сырой вывод удачных и неудачных прогонов.

## Порядок работы и тимейты

1. Прочитай PRD, текущий код и относящиеся к задаче тесты. Отметь последний выполненный микро-шаг и выбери ближайший незавершённый шаг в согласованном объёме.
2. Сформулируй проверяемый критерий. Для исправления ошибки сначала воспроизведи её минимальным тестом или зафиксируй исходный замер.
3. При наличии независимой части подключи тимейта с ограниченной зоной. Подходят сверка API со схемой, независимый обзор тестов и проверка браузерного сценария. Укажи файлы, ожидаемый результат и режим доступа. Не назначай двум тимейтам запись в одни файлы или запуск конфликтующих сценариев на одном стенде.
4. Внеси минимальное изменение. Ответственный за задачу сверяет выводы тимейтов с кодом, принимает решение по расхождениям и объединяет результаты.
5. Прогони целевые проверки. Если они красные, выясни причину и оставайся на текущем шаге. После зелёного результата прогони затронутую регрессию, проверь diff и запиши результат. К следующему шагу переходи после проверки текущего.
6. Сверь PRD, README и вывод тестов с поведением. Если менялась нагрузочная методика или стенд, запиши это рядом с результатами. Отмечай использование ИИ и отдельно записывай проверки, выполненные человеком.

| 05 | Реализовать атомарную запись пакета и отправитель с повтором | Выполнено. Проверены повторы, конфликт, откат и два писателя. |

## Обязательные проверки

| Изменение | Проверка |
|---|---|
| API, схема, ротация или пакет | `pytest` на реальном PostgreSQL в отдельной базе с суффиксом `_tests`. Проверить коды, форму ответа, ограничения, неизменность состояния при отказе и изоляцию. |
| React, снимок или SSE | `npm run build` из `frontend/` и Playwright. Для восстановления сверить отправленные точки, строки PostgreSQL и фактический DOM. |
| Повтор отправителя | HTTPX MockTransport для повторяемых и окончательных ошибок. Сверить байты запроса и прекращение повторов на `409`. |
| Согласованность при сбое | Проверить обычный сценарий и релевантный отрицательный контроль. Падение должно объясняться проверяемой регрессией. |
| Производительность | Сначала зафиксировать профиль, длительность и порог. Запускать отдельно от E2E. Записывать число точек, расхождения, p99, фактический темп и ресурсы. |

Полный набор запускается командами из [README.md](README.md). Шаг закрыт, когда целевая проверка и затронутая регрессия прошли, а для изменения поведения есть автоматический тест.
