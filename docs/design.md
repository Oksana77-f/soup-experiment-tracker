# Design of the experiment tracker

The tracker accepts batches of training metrics through `POST /runs/{id}/metrics` and displays them over SSE. FastAPI and React/TypeScript share an origin. PostgreSQL is the source for both the initial view and the stream.

**Ordering and retries.** Each request includes a client-generated `batch_id` and points with `name`, `step` and a finite numeric `value`. The server locks the project-owned run before inspecting existing receipts or points. It hashes the exact request body. A matching receipt returns the original acknowledgment, and a different body under the same run and batch ID returns `409`. An identical point within the same run, step and metric is ignored even under a different batch ID. A conflicting point rejects the whole batch. The transaction increments the run's `last_seq` by the number of new points and commits the points and receipt together. Unique constraints protect batch IDs, point identities and stream positions within each run. `seq` orders committed events. `step` orders the displayed points.

**Recovery.** The initial snapshot and `last_seq` come from one PostgreSQL statement. The browser opens SSE with `?after=last_seq`. Each metric carries `id: seq`, and `Last-Event-ID` takes precedence on a native reconnect. Replay and live delivery use the same indexed query for positions greater than the cursor. The reader drains bounded pages immediately and polls after an empty result. It releases the database connection before sending. A stalled send times out. After a terminal SSE error, the UI checks access and opens a fresh stream from the last applied position when service recovers. The sender repeats unacknowledged batches with the same bytes and ID. Application restarts preserve database state and the session signing secret.

**Isolation.** The sender uses a project-scoped write key in the Authorization header. The UI exchanges a read key for a signed, expiring HttpOnly cookie. The cookie can read the project's list, snapshot and stream. Mutating endpoints require a write key or use the local administration CLI. Session exchange uses a header key and validates the origin of browser requests. The server derives the project from the credential. Unknown and foreign run IDs return the same response, and protected responses use `Cache-Control: no-store`. Each SSE read checks revocation in the same query as the metrics. A previously fetched page is bounded and may already be in flight at rotation.

**Checks.** Compare sent points, PostgreSQL and the browser after deterministic stream interruption, including an intentionally broken replay control. Exercise cross-project access, concurrent duplicates, rollback, key rotation and restart. Evaluate 50 runs at 10 metrics/s with one observer per run against zero loss or duplication and p99 under 2 s from POST start to the visible row in a control browser.
