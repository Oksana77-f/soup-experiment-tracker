# PRD — Soup Experiment Tracker

Трекер принимает метрики обучения пакетами, хранит их в PostgreSQL и показывает на странице запуска через SSE. Пользователь видит данные своего проекта. После обрыва связи страница догружает пропущенные события. Вердикт для измеренного нагрузочного профиля зафиксирован в [отчёте](docs/results.md).

Сервер написан на Python и FastAPI. Интерфейс использует React и TypeScript. Node.js нужен для сборки фронтенда, а PostgreSQL хранит данные и подтверждения батчей.

## Утверждённое ТЗ

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-01 | Проекты, запуски и ключи | CLI создаёт демопроекты и запуски, выдаёт ключи чтения и записи и позволяет ротировать ключ. Ключи ограничены проектом и назначением. |
| FR-02 | Приём пакетов | Клиент отправляет пакеты в `POST /runs/{run_id}/metrics`, повторяя неподтверждённый пакет с прежним ID и теми же байтами. Повторы не создают новых точек. |
| FR-03 | Список и страница запуска | Пользователь входит по ключу чтения, видит запуски своего проекта и таблицу метрик выбранного запуска. |
| FR-04 | Живые обновления и восстановление | После снимка страница получает события по SSE. После обрыва, `502` или перезапуска приложения она догоняет зафиксированные данные по курсору. |
| FR-05 | Изоляция проектов | Чужой запуск нельзя читать, изменять или подписаться на его поток. Чужой и несуществующий UUID дают одинаковый ответ. Выход завершает сессию и убирает данные из открытых вкладок того же браузерного профиля. |
| FR-06 | Скрытые сбои | Проверены пропуски при переподключении, дубли, гонка двух писателей, зависшая отправка, частичная запись и ротация ключа при открытом потоке. |
| FR-07 | Запуск и сдача | Приложение запускается через `docker compose up`. Репозиторий включает инструкцию, одностраничную проектную записку, автотесты, сырой вывод и итоговую записку до двух страниц. Указаны ограничения проверок и использование ИИ. |
| NFR-01 | Нагрузка | 50 одновременных запусков по 10 метрик/с с одним зрителем на запуск. Критерии проекта — ноль потерь и дублей, выдержанный темп записи и p99 от начала отправки пачки до строки DOM в контрольном браузере меньше 2 с. Генератор ставит отметку после ожидания тика, перед сборкой JSON и первым POST. |

В MVP администрирование выполняется через CLI. Браузерные сценарии ограничены входом, просмотром и выходом. Графики, управление проектами из UI, долговременная очередь отправителя и доказательство масштабирования на несколько инстансов находятся вне текущей реализации.

Условия исходного задания предусматривают срок 48 часов и ориентир работы 5–7 часов. Репозиторий и материалы сдаются ответным письмом на `team@trysoup.dev`. После сдачи предусмотрено 40 минут живого обсуждения.

## HTTP API

UI, API и SSE обслуживаются с одного origin. Вход принимает `Authorization: Bearer <read_key>`, загрузка метрик — `Authorization: Bearer <write_key>`. После входа запросы чтения используют подписанную cookie `soup_session` с `HttpOnly`, `SameSite=Strict` и сроком действия 8 часов. На HTTPS добавляется `Secure`. Cookie не даёт права записывать метрики. Проект определяется по ключу или сессии.

| Метод и путь | Доступ | Успех | Ошибки по контракту |
|---|---|---|---|
| `GET /health` | Технический endpoint | `200`, `{"ok":true}` после проверки PostgreSQL | `503` при ошибке соединения с БД или тайм-ауте пула |
| `POST /api/session` | Bearer-ключ чтения. Если передан `Origin`, он должен совпадать с origin приложения. | `204`, устанавливает cookie | `401` для недействительного, отозванного ключа или ключа записи, `403` при чужом `Origin` |
| `POST /api/session/logout` | Требуется совпадающий `Origin` | `204`, отзывает предъявленную действительную сессию в PostgreSQL и очищает cookie | `403` при отсутствующем или чужом `Origin` |
| `GET /runs` | Сессия чтения | `200`, `{project, runs: [{id, name}]}`. Запуски отсортированы по имени. | `401` при недействительной сессии |
| `GET /runs/{run_id}` | Сессия чтения и свой запуск | `200`, `{id, name, last_seq, points}`. Снимок и курсор получены одним SQL-запросом, точки упорядочены по `seq`. | `401`, `404` для чужого или отсутствующего запуска |
| `GET /runs/{run_id}/access` | Сессия чтения и свой запуск | `204`. UI использует проверку при восстановлении после терминальной ошибки SSE. | `401`, `404` |
| `POST /runs/{run_id}/metrics` | Bearer-ключ записи и свой запуск | `200`, `{batch_id, inserted, last_seq}`. Повтор идентичного пакета возвращает исходное подтверждение. | `401`, `404`, `409` при конфликте, `413` при превышении размера тела, `422` при невалидном пакете |
| `GET /runs/{run_id}/events` | Сессия чтения и свой запуск | `200`, `text/event-stream`. Событие `metric` несёт `id: seq` и JSON точки. | `400` для невалидного курсора или позиции после `last_seq`, `401`, `404` |

Некорректный UUID в маршруте с `run_id` даёт `422`. Операционная ошибка PostgreSQL или тайм-аут пула до начала ответа отображаются как `503`. Остальные ошибки PostgreSQL отображаются как `500`. Ответы сессии и маршрутов `/runs` получают `Cache-Control: no-store`. При отказе доступа к существующему чужому и отсутствующему запуску одинаковы статус и тело ошибки.

### Запись пакета

Тело JSON содержит UUID `batch_id` и от 1 до 256 точек. Максимальный размер тела — 256 КиБ. У точки есть `name`, `step` и `value`. Имя начинается с латинской буквы, включает до 64 символов из букв, цифр, `_`, `.` и `-`. Шаг — целое число от 0 до `2^53 − 1`, значение — конечное число. Дополнительные поля отклоняются.

```json
{
  "batch_id": "68e089c7-3e54-4222-bfa6-0c98cdf39258",
  "points": [
    {"name": "loss", "step": 120, "value": 0.42},
    {"name": "loss", "step": 119, "value": 0.45}
  ]
}
```

- Сервер блокирует строку запуска до проверки пакета. Идентичные точки внутри пакета и в БД пропускаются. Новые записываются. Разные значения для одной пары `(name, step)` отклоняют весь пакет с `409`.
- Повтор `batch_id` в том же запуске сверяется по SHA-256 исходных байтов тела. При совпадении возвращается сохранённый ответ, включая исходный `last_seq`. При изменении байтов, в том числе форматирования JSON, возвращается `409`.
- Счётчик запуска увеличивается на число новых точек. Точки, счётчик и подтверждение записываются в одной транзакции. Только новые точки получают `seq`. Если новый пакет полностью состоит из совпадений, `inserted` равен нулю.
- Отправитель хранит неподтверждённый пакет в памяти. Он повторяет сетевые и временные HTTP-сбои с задержкой и ограничением числа попыток. `409` завершает попытки для пакета.

### SSE и ротация

При первом подключении UI передаёт `?after=<last_seq>`. При автоматическом переподключении непустой `Last-Event-ID` имеет приоритет над `after`. Курсор по умолчанию — 0. Один и тот же запрос возвращает зафиксированные события `seq > cursor` в порядке `seq`.

```text
id: 42
event: metric
data: {"seq":42,"name":"loss","step":119,"value":0.45}
```

Порция содержит до 100 точек. При наличии строк сервер переходит к следующей порции сразу после отправки текущей. После пустой порции ждёт секунду. Соединение с БД освобождается перед отправкой. Тайм-аут отправки кадра данных — 3 с. Keepalive использует отдельный путь библиотеки SSE, который не покрыт этим тестом. SSE передаёт подсказку о повторе через 1 с и отправляет keepalive каждые 15 с.

Страница применяет события последовательно, игнорирует повторный `seq` и при разрыве в последовательности восстанавливает поток с последнего применённого номера. В состоянии `CONNECTING` переподключение выполняет браузер. При `CLOSED` UI проверяет доступ через `/access` и открывает новый `EventSource` с последнего применённого номера. При `401` UI возвращается ко входу.

После ротации новый запрос со старым ключом отклоняется. Сессия чтения хранит ID ключа и уникальный ID сессии. Запрос каждой порции проверяет отзыв ключа, отзыв сессии и доступ к запуску вместе с выборкой метрик. Для пустого потока следующая проверка следует после ожидания до 1 с плюс время SQL и планирования. Локальный тест с этим интервалом требует завершения потока за 2 с после коммита ротации. Уже полученная для отправки порция может быть в пути. Запрос записи, прошедший проверку ключа до ротации, может завершить запись.

Выход и замена cookie при новом входе отзывают только предъявленную сессию. Список, снимок, проверка доступа и SSE отклоняют копию отозванной cookie и после перезапуска приложения. На том же процессе сигнал отзыва прерывает ожидание открытого SSE и останавливает дальнейшую отправку кадров. Другой процесс узнает об отзыве при следующем запросе к БД. Кадр, отправка которого уже началась, может дойти до клиента. Другие вкладки получают сигнал изменения сессии через `storage` и заново проверяют доступ. При отключённом хранилище защита запросов и потоков остаётся серверной.

## Структура PostgreSQL

Источник схемы — [tracker/schema.sql](tracker/schema.sql). Один проект имеет много запусков и историю ключей. У запуска есть множество метрик и подтверждений пакетов.

| Таблица | Поля | Ключи и ограничения |
|---|---|---|
| `projects` | `id uuid`, `name text` | PK `id`, уникальное имя |
| `api_keys` | `id uuid`, `project_id uuid`, `scope text`, `digest text`, `revoked_at timestamptz` | PK `id`, FK на проект, уникальный SHA-256 дайджест. Scope `read` или `write`. Частичный уникальный индекс `(project_id, scope) WHERE revoked_at IS NULL`. |
| `revoked_sessions` | `digest text`, `expires_at timestamptz` | PK `digest`, индекс `expires_at`. Отзыв хранится как хеш подписанной идентичности сессии. Для старых cookie идентичность вычисляется из ID ключа и времени выдачи. Истёкшие записи удаляются при следующем отзыве. |
| `runs` | `id uuid`, `project_id uuid`, `name text`, `last_seq bigint` | PK `id`, FK на проект, `UNIQUE (project_id, name)`. `last_seq` начинается с 0 и ограничен безопасным диапазоном JS. |
| `metrics` | `run_id uuid`, `seq bigint`, `name text`, `step bigint`, `value double precision` | PK `(run_id, seq)`, FK на запуск, `UNIQUE (run_id, name, step)`. `seq` от 1, `step` от 0, оба в безопасном диапазоне JS. |
| `receipts` | `run_id uuid`, `batch_id uuid`, `digest text`, `acknowledgment jsonb` | PK `(run_id, batch_id)`, FK на запуск. Хранит хеш исходного тела и первоначальный ответ. |

В БД остаются хеши ключей. Docker Compose хранит БД и секрет подписи сессий в отдельных томах, чтобы перезапуск приложения сохранял данные и сессию.

## Экраны

`GET /` и `GET /view/{run_id}` отдают оболочку React. При отсутствии сборки ответ — `503`. Статика сборки обслуживается через `/assets`. Данные запрашиваются отдельно по защищённым маршрутам API.

| Экран | Содержание и действия | Состояния |
|---|---|---|
| **Sign in** | На `/` или `/view/{run_id}` при отсутствии действительной сессии. Ввод ключа чтения, отправка формы, переход к списку или выбранному запуску. | Ожидание отправки, неверный или отозванный ключ, ошибка связи |
| **Training runs** | На `/` при активной сессии. Имя проекта, список запусков, ссылки на страницы запусков и выход. | Загрузка, пустой список, ошибка чтения |
| **Experiment run** | На `/view/{run_id}`. Имя запуска, переход к списку, статус связи, число точек, последний `seq` и таблица `Step / Metric / Value / Sequence`. Строки сортируются по `step`, при равном шаге — по имени метрики. | `Loading`, `Live`, `Reconnecting`, `Offline`, пустая таблица и сообщение об ошибке. `Live` показывает открытое соединение. |

## Проверка и текущий статус

Контракты записи, границ входа, курсора, ротации и доступа проверяются в [tests/test_api.py](tests/test_api.py). Браузер сверяется с исходным набором и прямым чтением PostgreSQL в [tests/test_stream.py](tests/test_stream.py). Там же проверяются обрыв, `502`, смена проекта в одном браузере, рестарт и зависшая отправка. Отрицательные контроли отключают догрузку или блокировку только в тестовых фикстурах. Команды запуска находятся в [README.md](README.md).

Для диагностики записи оператор может включить внутренний лог с длительностями получения соединения, запроса блокировки и успешного коммита. По умолчанию лог отключён. Границы замеров описаны в [README.md](README.md#inspect-batch-write-timings).

Реализация и проверки корректности подтверждены. Минутный прогон шага 12 прошёл на локальном стенде. Доставлены все 30 000 метрик без потерь и дублей при p99 до DOM 1,68 с. Генератор работал отдельно от контейнеров приложения и БД на той же машине. Контрольный прогон шага 14 подтвердил результат. Доставлены все 30 000 метрик при p99 до DOM 1,61 с. Вердикт — **SHIP для проверенного локального профиля** с одним зрителем на запуск. Расширенный прогон с пятью зрителями подтвердил доставку всех событий, но p99 до DOM вырос до 2,65 с при пороге 2 с. Для этого профиля вердикт — **DON’T SHIP**. Числа, методика и границы проверки приведены в [docs/results.md](docs/results.md). Порядок дальнейших работ закреплён в [rules.md](rules.md).
