# Журнал использования ИИ

Запись до начала реализации, 10 ноября 2026 года. Пункты ниже описывают обсуждение и проверку плана. Результаты выполнения тестов будут записаны отдельно после запуска.

| Участок | Что предложили или заметили | Как изменили план |
|---|---|---|
| Разбор PDF | ИИ извлёк требования, веса оценки, условия сдачи и различия между тремя ролями | Выбран Full-Stack. Требования сверены с PDF. Отдельные проценты за рестарт или красный прогон в документе не заявлены |
| Стек | ИИ предложил простой JavaScript. Пользователь попросила выбрать более интересный язык для браузера | Выбраны TypeScript, React и Vite с одним адресом для UI и API |
| Срок | План пользователя был оценён в рамках задания, но сумма этапов составляла 7 ч 30 мин | Пользователь подтвердила арифметическую ошибку. Рабочий ориентир — 6 ч 30 мин |
| Поток | В заметке пользователя был переход между replay и live через pub/sub. ИИ предложил один запрос по курсору для обоих режимов | Пользователь приняла общий источник. LISTEN/NOTIFY оставили кандидатом на оптимизацию после замеров |
| Выдача seq | Пользователь показала, как PostgreSQL sequence допускает поздний коммит seq=5 после выдачи seq=6 | ИИ сверил поведение sequence и блокировок с документацией. Зафиксировали счётчик на запуск, блокировку до проверки существующих точек и единый коммит |
| Батчи | Пользователь предложила обработку частичного пересечения, конфликт по хешу и тест повтора с новым ID после потери ACK | Добавили правила, ограничили batch_id запуском и зафиксировали хеширование точных байтов |
| Красный тест блокировки | Пользователь предложила отключить FOR UPDATE в тесте порядка. ИИ указал, что UPDATE счётчика всё равно сериализует присвоение номеров | Заменили проверяемый контракт на два успешных конкурентных батча с одной новой точкой. Пользователь добавила детерминированную синхронизацию. В зелёном прогоне ожидаем блокировку второго запроса, а в красном допускаем оба до точки вставки |
| SSE и 502 | Пользователь предупредила, что 503 на тестовом гейте остановит нативные повторы и что прокси может вернуть 502 при рестарте | ИИ сверил стандарт EventSource и развёл два теста. Для обрыва держим запрос, затем отвечаем 200. Для 502 проверяем восстановление нового EventSource с последнего применённого номера и остановку при отказе в доступе |
| Ротация и CSRF | Пользователь указала на стоимость проверки ключа, окно при кешировании и риски cookie для записи | Приняли проверку актуальности в том же SQL-запросе, без кеша, и явно разделили cookie для чтения и заголовок для записи |
| Нагрузка | Пользователь предложила заранее записать порог и добавить пять зрителей на запуск | Приняли p99 до DOM < 2 с для базового прогона. Пять зрителей — дополнительный замер. В отчёте отдельно покажем SSE и браузер |

Источники для технических сверок: [PostgreSQL sequence](https://www.postgresql.org/docs/current/functions-sequence.html), [блокировки](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS), [изоляция](https://www.postgresql.org/docs/current/transaction-iso.html), [EventSource](https://html.spec.whatwg.org/multipage/server-sent-events.html) и [HTTP-кеш](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.5).


## Реализация и проверка

- Codex подготовил схему PostgreSQL, обработчик записи, SSE, React UI, тесты и нагрузочный сценарий. Пользователь определила требования к гонке, ротации и CSRF в обсуждении. Ручная проверка кандидатом пока не отмечена.
- Для гонки зелёный тест ожидал наблюдаемую блокировку второго запроса в PostgreSQL. Красный тест держал оба запроса после проверки новой точки. С блокировкой два ответа 200 и одна запись. Без неё получены 200 и 500 с SQLSTATE 23505. Сырой вывод находится в evidence.
- Стоимость повторной проверки read-ключа учтена в проекте. SSE проверяет активный ключ и читает порцию одним SQL-запросом. Cookie не даёт права записи. Дополнительно реализованы проверка Origin для входа из браузера и обязательный same-origin для выхода.
- При первой сборке TypeScript обнаружил синтаксическую ошибку в разборе пути. Заменили выражение на явный разбор пути и пересобрали. Аудит зависимостей сборки выявил два замечания. Обновили Vite и esbuild и получили ноль замечаний при повторном аудите.
- Codex проверил в реальном Chrome вход, поток, позднюю точку, дедупликацию, межпроектный отказ, ротацию ключа, обычное переподключение, отдельный ответ 502 и восстановление после реального рестарта контейнера приложения. Прогоны сохранены отдельно.


- Первый полный набор обнаружил, что библиотека SSE оставляла общий флаг остановки между тестовыми серверами в одном процессе. Сбросили его в фикстуре и убрали искусственный тайм-аут отправки 120 мс из обычных браузерных сценариев. Итоговый результат — 11 из 11. Оба ранних отчёта сохранены.
- Первые минутные нагрузки не прошли заявленный порог. Во втором прогоне один POST оборвался до подтверждения. Исправили способ подсчёта пропущенных значений отдельно от номеров событий и применили в генераторе политику повторов клиента. Короткий повтор с этой версией прошёл с 15 000 точек и p99 до DOM 1,64 с. Счётчик повторов остался нулевым. Все три результата сохранены. Итог для устойчивой нагрузки оставили DON’T SHIP.

- На шаге 11 Codex добавил опциональные таймеры POST. Тимейт независимо сверил границы получения соединения, запроса блокировки и коммита, включая повтор с прежним подтверждением и откат. Проверены 16 тестов и четыре записи журнала в Compose. В одной записи PostgreSQL подтвердил ожидание блокировки, а конфликт оставил время коммита пустым. Это контроль замеров перед минутным прогоном.

- На шагах 12–13 Codex провёл минутный прогон и разобрал 3 000 таймингов POST. Тимейт независимо пересчитал p99, 30 самых медленных запросов и остаток после первых 50 строк. Порог пройден, поэтому согласованное условие для правки кода не сработало. Генератор и Compose делили одну физическую машину.

- На шаге 14 Codex повторил минутный профиль и сверил исходники генератора, образ приложения, версию PostgreSQL и Chromium с шагом 12. Сырой вывод подтвердил 30 000 доставленных метрик, отсутствие потерь и дублей и p99 до DOM 1,61 с. Вердикт SHIP ограничен проверенным локальным профилем.

- На шаге 15 Codex повторил минутный профиль на том же образе с пятью зрителями на запуск. Проверены 30 000 метрик в БД и 150 000 доставок подписчикам. Тимейт независимо сверил задержки и ресурсы. p99 до DOM 2,65 с превысил порог. Вердикт для пяти зрителей — DON’T SHIP, для одного — SHIP. Сырой результат сохранён.

- Перед сдачей Codex проверил из свежего клона вход и появление строк в Chromium, затем прогнал 16 тестов в контейнере с PostgreSQL и Chromium. Тимейт предложил отдельно проверить возврат к чужому запуску через историю браузера и уточнил формулировки записки о повторах, откате и логах. Первый проверочный скрипт искал Chromium в стандартной папке и остановился до входа. Указание пути к уже установленному браузеру исправило запуск. [Первый вывод](../evidence/fresh-clone-preflight.txt) · [Демо и полный прогон](../evidence/fresh-clone-compose.txt)

- При редактуре записки пользователь запросила точные границы p99, число проверок SSE и замер окна ротации. Codex сверил отметки времени с кодом, измерил SQL-чтения на двух профилях, добавил тест завершения писателя до коммита и проверил ротацию на интервале 1 с. Причину всего роста p99 по агрегатам установить не удалось. Успешный прогон 17 тестов использовал ранее собранный образ из-за тайм-аута PyPI.
